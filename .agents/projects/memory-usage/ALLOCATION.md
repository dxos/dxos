# Where Composer's memory goes, for a JavaScript developer

Numbers here are footprint deltas measured with
`packages/apps/composer-app/scripts/memory/ledger.mjs --detached` against
production builds, Chromium 153, macOS. Footprint is what the OS charges the
process; the allocator nodes are accounting and do not track it reliably. The
harness [README](../../../packages/apps/composer-app/scripts/memory/README.md)
explains the difference.

Always measure with `--detached`. A Playwright-driven page adds ~130 MB of its
own to this app.

Every measurement below is n=1 per fixture, and the blank-page baseline in this
harness varies 34.5–37.2 MB between runs. Treat anything under ~3 MB as noise.

## What a thing costs

Each row is one pair of pages differing in one variable, generated by
`scripts/memory/cost-fixtures.mjs`, measured as the change in process footprint.

| What you do                                            | Footprint cost | Largest contributor       |
| ------------------------------------------------------ | -------------- | ------------------------- |
| Hold 1 MB in an `ArrayBuffer`, anywhere in the process | **1.02 MB**    | `partition_alloc`         |
| Spawn one dedicated worker                             | **~2.6 MB**    | `v8`, `malloc`            |
| Ship one more ES module                                | **~24 KB**     | `malloc` 62%              |
| One element with 6 CSS custom properties               | **~1.2 KB**    | `malloc`                  |
| One element with a class list matching 9 rules         | **~0.8 KB**    | `malloc`                  |
| Make one more HTTP request while loading               | **~6.6 KB**    | `malloc`, `web_cache`     |
| Ship one more function                                 | **~0.5 KB**    | `v8` 47%, `web_cache` 27% |

The "largest contributor" column is a share of the footprint delta, not a
partition of it. No single allocator node accounts for a whole row, and in the
DOM rows the `malloc` node moves several times further than the footprint does.

**Binary data costs the same wherever it lives.** 80 MB of `ArrayBuffer` held
inside a dedicated worker moved the renderer's footprint by 81.8 MB. Dedicated
and shared workers run inside the creating renderer process, so moving bytes into
one moves the work, never the memory. Only a service worker gets its own process.

**Module count beats module size.** The same 1.95 MB of JS costs 42.9 MB as one
module and 73.6 MB as 1,000. A control that fetches the same 1,000 files and
discards the text costs 6.6 MB, so about a fifth of that gap is the requests.

## What Composer spends it on

An idle tab, fresh profile, nothing opened. Six `--detached` runs put the app's
main renderer at **417–445 MB, median 437**. Quote the range, not a single run.
There is also a second app renderer at ~64 MB that exposes no CDP target, so the
whole app is ~509 MB and ~64 MB of it goes unread.

### Just having the code — 97 MB

Composer loads ~920 scripts holding 57,354 functions and 12.55 MB of source,
counted with `Profiler.takePreciseCoverage`.

A synthetic page approximating that shape, 927 modules and 56,547 functions and
13.28 MB of source, doing nothing at all, costs **96.9 MB**. No React, no DOM, no
workers. Roughly 22% of the tab before any of it runs.

Two caveats. The fixture is close but not exact, 1.4% fewer functions and 5.8%
more source. And it retains 17.4 MB of `web_cache` against the real app's 2.7 MB,
so it overstates by holding source Composer has already dropped.

About 35 MB of that 97 is the blank-renderer baseline, which is also inside every
other figure on this page, including Composer's own 437.

### The JS objects — 82 MB

Live JS heap across every realm. Sampled allocation attributes 51 MB of churn to
packages, led by `effect` at 18.6 MB and `@dxos/echo` at 10.9 MB. That is
allocation volume, not retention: it says which code churns, not which code
holds.

### Unexplained Blink allocation — ~100 MB

`partition_alloc/allocated_objects/<unspecified>` is 89–112 MB across the six
runs, median 100. This is the largest single unknown in the tab, and no
instrument available here names it. It is C++ allocation inside Blink that no
memory-infra dump provider claims.

It scales with how much SDK is running:

|                                                   | `<unspecified>` |
| ------------------------------------------------- | --------------- |
| `recovery.html`, ECHO client, in-page, no plugins | 12.7 MB         |
| `todomvc`, worker client, minimal UI              | 37.2 MB         |
| `composer`                                        | 112.4 MB        |

**It is tempting to call this binary data, and the evidence does not support
that.** `ArrayBuffer` bytes do land in this node one for one, but the converse
does not follow, and three things argue against it:

- The named `partition_alloc/partitions/array_buffer` node is only 4.29 MB.
- V8's own external-memory accounting for the page realm is 13.25 MB. Worker
  realms report zero because `performance.memory` is Window-only, but those
  worker heaps are 0–0.8 MB, so there is no room for 100 MB of JS-visible buffers
  hiding in them.
- The ladder is correlation. `malloc`, `v8` and this node all grow together
  across the three rungs, and the rungs are not clean controls: `recovery.html`
  runs no workers at all, and todomvc has no service worker.

The defensible statement is the layered one: Composer's own layer adds ~75 MB to
this node over todomvc, and naming it needs a symbolized Chromium, which Chrome
for Testing does not publish.

### DOM, CSSOM and the perf timeline — 31 MB

`blink_gc`. Composer's DOM is small at rest, 3,055 elements, so element count is
not the driver.

The largest named entry is `PerformanceMeasure` at 6.5 MB in a worker, with 2,094
live marks and 1,750 measures at idle against todomvc's 7 and 14. Nothing clears
them. Treat 6.5 MB as an upper bound rather than a reclaimable total: it is read
from `blink_objects`, which restates `blink_gc` by class, and that worker's whole
Oilpan heap is 3.4 MB.

### WebAssembly

Invisible to every allocator node and every JS heap API; the harness measures it
by shimming `WebAssembly.Memory`. Within one `--work` run, committed linear
memory goes from 28.4 MB at boot to 165.7 MB with 200 tasks and 3 documents open,
of which 146.6 MB is automerge across three instances, because the bundle ships
two distinct automerge Rust binaries and the tab runs its own replica alongside
the worker's.

Committed is not resident. At that same checkpoint only 24.8 MB was resident, so
today's reclaimable figure is far smaller than the committed one, and grows as
pages are touched.

## Where the 445 MB actually sits

This is the decomposition that sums, from the highest of the six runs. Unlike a
budget of mechanisms, these are the allocator's own numbers and they add up to
the footprint, give or take the 2% the ledger cannot place.

| Node              |  MB | What is known about it                                          |
| ----------------- | --: | --------------------------------------------------------------- |
| `malloc`          | 175 | ~37 MB is the code-shape fixture; the rest has no mechanism     |
| `partition_alloc` | 125 | 112 of it `<unspecified>`; no mechanism, largest single unknown |
| `v8`              | 117 | 82 MB is the live JS heap; the rest is code metadata            |
| `blink_gc`        |  31 | DOM and CSSOM, incl. up to 6.5 MB of uncleared perf entries     |
| misc              |   7 | `web_cache`, `discardable`, `skia`                              |
| WebAssembly       |   4 | outside every node; 166 MB committed once documents are open    |

Compositor and GPU memory is absent on purpose: the ledger excludes it from the
renderer's private footprint, so it is not inside the 445.

Two named results sit across this table rather than inside one row. The
code-shape fixture costs 96.9 MB spread over `malloc`, `v8` and the ~35 MB blank
baseline. The live JS heap is 82 MB of the `v8` row. Together they are the only
parts of the tab with a demonstrated cause, roughly 40% of it.

## What this says to do

1. **Clear the perf timeline.** Up to 6.5 MB, named, idle, with no reader. The
   smallest item here and the only unambiguous one.
2. **Ship fewer modules.** 920 of them cost roughly 22 MB in per-module overhead
   plus 6 MB in requests, independent of the bytes inside.
3. **Collapse the duplicate automerge instances.** Two Rust binaries plus a
   tab-side replica, 146.6 MB committed once data is open, 24.8 MB of it resident
   at the point measured.
4. **Find out what the ~100 MB of Blink allocation is** before optimising
   anything else. Largest slice, and the only one with no mechanism behind it.

## Reproducing

Run the ledger from `packages/apps/composer-app`; the relative paths below assume
it. Production builds only, `vite serve` numbers are not comparable.

```bash
moon run composer-app:bundle
moon run todomvc:bundle
pnpm --filter @dxos/composer-app exec vite preview --port 4173 &
pnpm --filter @dxos/todomvc exec vite preview --port 4174 &

# Composer, the headline number.
node scripts/memory/ledger.mjs http://localhost:4173 --detached --settle 25

# Which package allocates the JS.
node scripts/memory/ledger.mjs http://localhost:4173 --detached --by-code

# Composer's own layer over the same SDK.
node scripts/memory/ledger.mjs http://localhost:4174 --detached --ready none --json ./tmp/todomvc.json
node scripts/memory/ledger.mjs http://localhost:4173 --detached --baseline ./tmp/todomvc.json

# The per-unit table: generate the fixtures, serve them, measure each pair.
node scripts/memory/cost-fixtures.mjs ./tmp/fixtures
(cd ./tmp/fixtures && python3 -m http.server 4180) &
node scripts/memory/ledger.mjs http://localhost:4180/one/ --detached --ready none --settle 12
node scripts/memory/ledger.mjs http://localhost:4180/many/ --detached --ready none --settle 12
```
