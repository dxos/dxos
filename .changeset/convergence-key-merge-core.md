Entities can declare a `meta.convergenceKey`: a caller-supplied domain identity, unique within a space, so that state initialized independently by several peers converges instead of accumulating duplicates. The id stays a surrogate — system-minted and random — and the convergence key sits alongside it, distinct from `meta.key`/`meta.version`, which record the registry entry an instance was created from (provenance, not identity). The key is an opaque string; callers that need generations encode them in it (`com.example.seed@2`), which yields distinct entities because the strings differ.

The identity is declared by assigning the meta field inside an update callback — `Entity.update(x, (x) => { Entity.getMeta(x).convergenceKey = '…' })` — so the write batches with the caller's other changes; there is deliberately no dedicated setter, and no new public API surface at all. The deterministic core lives in the worker (`@dxos/echo-host`): `mergeCandidates` computes the merged state over the whole candidate set at once — the winner is the minimum id, and each field takes the value from the smallest-id candidate that defines it. That is deliberately not a pairwise fold, which would not be associative and would let different application orders diverge. The one piece the client keeps, in `@dxos/echo/internal`, is `resolveMergeRedirect`: it follows the `system.mergedInto` written on a merged-away entity, transitively and without trusting the data — an edge that fails to decrease the id ends the chain, so cycles and forward references terminate.

The winner records `system.mergedFrom`, the ids of everything folded into it — the reverse edge of `mergedInto`, stored rather than derived because finding it the other way means scanning for entities that point here, which no index supports. It is transitively closed, so a collapsing chain carries absorbed ids forward. Losers are tombstoned rather than erased, so every recorded id still resolves.

Merging is automatic, and it runs in the worker: every indexing batch reports the convergence keys it saw, a point lookup on the new `objectMeta.convergenceKey` column finds collisions, and the merge executes against the raw automerge documents — once per device, at the moment a duplicate replicates in, with no client, query, or scan involved. Each merge writes per field rather than replacing the object (a replace would rewrite every field, so a concurrent edit to a property the merge never touched would lose the last-write-wins race), records `system.mergedInto` and the loser's heads, and tombstones the loser. The merge's own writes re-index the tombstones, which removes losers from query results everywhere; the client query path additionally drops entities the index still reports live, read-only, to cover the moment between the tombstone replicating and the local index catching up. The guarantee is eventual (about one indexing cycle): a query racing the merge can briefly return both copies before settling.

Reference rewriting is index-driven and also runs in the worker: the reverse-reference index names each referrer of a merged-away loser and the exact property holding the ref, so repointing is a point load per referrer — no client, no scan, and deliberately no `Filter.everything()` anywhere. It runs right after a merge's tombstones and again whenever a re-indexed loser is serviced, which is what catches referrers written concurrently with the merge. Rewriting is an optimization plus the compatibility path for clients too old to follow `mergedInto` — losers keep replicating rather than being erased, so a reference that was never rewritten still resolves through the redirect.

The redirect is durable, not advisory. Reference resolution follows `system.mergedInto` — sync and async — so a reference that was never rewritten reaches the survivor instead of dangling. The worker services already-redirected entities when they re-index: a straggler peer's late edits are folded into the winner via the recorded watermark, and a loser resurrected by `db.add` is re-tombstoned with its restore-time edits carried across, which makes the redirect sticky without special-casing the restore path. Convergence keys are limited to objects, enforced at every engine layer — detection, the worker's re-verification, and the client's query collapse each ignore keyed relations and empty strings, since the field replicates from peers that cannot be trusted to have validated it — merging a relation would tombstone it without reconciling its endpoints. Devices upgrading from builds that predate the index column re-index once so existing duplicates become detectable, and `@meta` stays out of full-text search matching and reverse-reference extraction for document objects.

Detection is crash-proof: convergence keys seen while indexing are recorded as durable intents in the same transaction as the index cursors, and cleared only once the merge pass services them — a fault or a crash between indexing and merging is retried on the next pass rather than silently dropped. The worker reads, computes, and writes each merge in one synchronous block (an edit replicating in mid-merge can no longer slip below the tombstone's watermark), advances a fold watermark only when the fold actually applied, flushes the winner's folded data durably before writing any tombstone — and every loser's tombstone before clearing the intent that would retry it — and declines to merge an entity whose key changed or that was deleted mid-flight — deletion is respected, not merged. Reference rewriting sits outside these guarantees on purpose (a ref left behind still resolves, and the loser's next re-index re-presents the work), and it never writes to a merged-away referrer, so a mechanical rewrite can never masquerade as a straggler's edit.

Deletion transitivity follows the redirect: a relation whose endpoint — or an object whose parent — was merged away is judged at the surviving entity, so it stays in query results while the survivor lives instead of vanishing with the tombstone. Field names that collide with `Object.prototype` members (`toString`, `constructor`, `__proto__`, …) merge like any other field. And when two devices merge the same duplicates concurrently, the straggler fold reads its watermark as the union of every device's record, so it never rewinds the winner to values a concurrent fold already carried across.
