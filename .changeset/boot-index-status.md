'@dxos/echo': minor

The ECHO host reports what its index is doing, so an app can show index migrations and a rebuild after an upgrade instead of appearing to hang.

- `@dxos/protocols`: `DataService.IndexStatus` (`migrating`, `indexing` or `idle`, with `done` of `total`), the work a boot screen or deadline waits on, and `DataService.IndexActivity` (optional `catchUp` and `fullText` progress), the work queries answer through. `DataService.subscribeIndexStatus` and `DataService.subscribeIndexActivity` each send the current value and then each change.
- `@dxos/echo-host`: `EchoHost.indexStatus` counts pending index migrations before running them and reports each store as it migrates. After opening, and at most once a second while passes leave work behind, it counts the backlog: documents with no primary-index cursor and the feed blocks of the host's spaces stored before it opened are the rebuild, and feed blocks stored later are catch-up, as are indexed documents whose heads moved on, counted by the same pass. A pass that drains ends both. Every document the indexer reads now gets a cursor, including ones with nothing to index (space roots, credentials, outdated directories, ones with no space) and ones whose read throws, so a document with no cursor is one not read yet, and none is loaded again on every pass. A full-text flush reports the objects the full-text index has yet to reach, counted at most once a second, until it finishes or fails; flushes run one at a time. A count that fails leaves progress as it was.
- `@dxos/index-core`: `IndexEngine.pendingMigrations()`, `migrate({ onProgress })`, `IndexEngine.primaryIndexNames` and `IndexEngine.countSecondaryBacklog()`. A data source asked with `countCatchUp` reports `catchUp` from `getChangedObjects`, and `IndexingResult.catchUp` carries it. A batch with no objects still writes the cursors that moved, and the pass goes on past them.
- `@dxos/sql-sqlite`: `SqlMigrations.pending(migrations, table)` lists the migrations a `Migrator` history table has not recorded yet.
- `@dxos/worker-framework`: a worker's runtime can send `status` messages before `ready`. Each one restarts the leader handshake deadline and the connection's initial-open deadline, so a long but progressing start is no longer cut off at 15 s. `Connection.workerStatus` exposes them.
- `@dxos/client`: `Client.indexStatus` reports the status from the worker while the client opens, then from the host's stream; the worker stops sending at `ready`. `Client.indexActivity` follows the host's activity.
