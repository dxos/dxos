# Spike: SchemaAST port + v3→v4 persisted-schema compatibility

Ported ECHO's critical-path Effect-Schema code to `effect@4.0.0-beta.105` and proved that JSON
Schema documents written by Effect 3 can be read back into Effect 4.

**Result: both work.** 106 tests pass, `tsc --noEmit` is clean. Reproduce with
`npm install && npm test` (this directory is deliberately outside the pnpm workspace so it can
pin effect 4 without touching the monorepo lockfile).

## What was built

| File                        | LOC | What it is                                                                   |
| --------------------------- | --- | ---------------------------------------------------------------------------- |
| `src/ast.ts`                | 449 | Port of `packages/common/effect/src/internal/ast.ts` (535 LOC) to the v4 AST |
| `src/json-schema-compat.ts` | 279 | Port of ECHO's `toEffectSchema`, reading **v3-persisted** documents          |
| `test/compat.test.ts`       | 210 | 20 tests over a real v3 fixture                                              |
| `test/writeback.test.ts`    | 67  | 3 tests sizing the write path                                                |

`fixtures-v3.json` is not hand-written — it was generated by running `toJsonSchema` from
`@dxos/echo` on HEAD (effect 3.21.4) against two `Type.makeObject` types covering refinements,
formats, refs, nested structs, records, literal unions, `Any`/`Unknown`, and optionality.

## AST mapping (v3 → v4)

| v3                                                               | v4                                                                         |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `TypeLiteral`                                                    | `Objects`                                                                  |
| `TupleType`                                                      | `Arrays` (`rest` holds bare ASTs, not `Type` wrappers)                     |
| `Refinement` node + `.filter`                                    | `checks: ReadonlyArray<Check>` on the constrained node                     |
| `StringKeyword` / `NumberKeyword` / …                            | `String` / `Number` / …                                                    |
| `PropertySignature{name,type,isOptional,isReadonly,annotations}` | `PropertySignature{name,type}`; the rest moved to `type.context`           |
| `encodedBoundAST`                                                | `toEncoded`                                                                |
| `getPropertySignatures(ast)`                                     | no equivalent — hand-rolled (unwrap `Suspend`, read `.propertySignatures`) |
| `Union.make(types, ann)`                                         | `new Union(types, mode, ann, …)` — `mode: 'anyOf' \| 'oneOf'` is new       |
| symbol annotation IDs                                            | **string** annotation keys                                                 |

Straight ports, no semantic surprises: `isOption`, `isLiteralUnion`, `isArrayType`, `visit`,
`findNode`, `findProperty`, `getDiscriminatingProps`, `getDiscriminatedType`.

## Three findings that change the migration estimate

### 1. `SchemaAST` is effectively private in v4

**129 of its 138 exports are marked `@internal`** and are absent from the published `.d.ts`.
Gone from the typed surface: `annotate`, `annotateKey`, `isMutable`, `replaceContext`,
`replaceChecks`, `appendChecks`, `struct`, `union`, `tuple`, `record`, `getAST`. What remains
public is the node classes (constructible), the `is*` guards, `isOptional`, `resolve*`,
`toEncoded`/`toType`, `mapOrSame`, `optionalKey`, `decodeTo`, `flip`.

The port works entirely on public API, but three helpers had to be re-expressed:

- `SchemaAST.annotate(ast, ann)` → `Schema.make(ast).annotate(ann).ast`
- `SchemaAST.isMutable(ast)` → `ast.context?.isMutable ?? false`
- `SchemaAST.replaceContext(ast, ctx)` → rebuild via `Schema.optionalKey` / `Schema.mutableKey`

This is the single biggest risk in the Schema tier: DXOS's approach of reaching into the AST is
tolerated but unsupported, and `effect/unstable/*` carries no semver guarantee. Any of these
shims can break in a minor release.

### 2. Annotations on a checked node move to the check

`.annotate()` on a schema that carries checks attaches to the **last check**, not the node —
and `SchemaAST.resolve` reads back only the last check's annotations, ignoring the node's own.
So `ast.annotations.title` silently returns `undefined` for any refined type.

Every annotation read in ECHO must go through a resolver (`src/ast.ts` exports
`resolveAnnotations`). This is a compile-clean, test-silent failure mode — the kind that shows
up as blank form labels rather than a stack trace. Worth a lint rule during the migration.

### 3. Optionality changes shape on the way out

v3 wrote an optional field as the bare type, omitted from `required`. v4's emitter writes
`anyOf: [T, {type: "null"}]` **and** omits it from `required`. Every optional field in every
emitted document changes shape.

## Read path (v3-persisted → v4): solved

All 20 tests in `test/compat.test.ts` pass against the real fixture, including:

- ECHO type identity (`typename`, `version`, `entityKind`, `dxn:` `$id`) → v4 annotations.
- Correct required/optional split for all 11 properties.
- `propertyOrder` (DXOS extension) preserved.
- **v3-only sentinels decoded**: `{"$id": "/schemas/unknown"}` → `Unknown`,
  `{"$id": "/schemas/any"}` → `Any`, `/schemas/{}` → empty struct. v4 emits none of these, so
  they exist only in already-stored data and would otherwise silently degrade to `Unknown`.
- `/schemas/echo/ref` → a live `Schema.declare` that still carries the target DXN.
- Refinements → v4 `Check`s that still validate (`age` rejects `-1`, `200`, `4.5`).
- `pattern`/`format` on `email` still validates and annotates.
- A real object validates end-to-end; bad enum value, out-of-range number, and a missing
  required field are all correctly rejected.

Both ECHO annotation namespaces (`echo` and `annotations`) are handled, matching the merge
behaviour already in `json-schema-type.ts:387` from the previous format migration.

## Compatibility is only needed in one direction

DXOS has few enough deployed clients that cross-version reads are not a concern: **v4 must read
v3-written data, but v3 never has to read v4-written data.** That constraint removes the entire
"emit a v3-shaped document" problem below — it matters only if old clients must keep reading.

What it does introduce is a permanently **mixed** space: existing `Type` entities keep their v3
`jsonSchema` payload until rewritten, new ones are written v4-native. `src/dispatch.ts` handles
this, and `test/dispatch.test.ts` proves it (5 tests):

- The formats are structurally distinguishable — a representation document has
  `{representation, references}`, which a v3 JSON Schema document never has. No version field
  needs to be added to already-written data (though adding one going forward is cheaper than
  relying on shape).
- v4 reads a v3-written document, and reads its own v4-written document, through one entry point.
- The v3 → v4 rewrite is lossless for type identity, per-property optionality, and validation
  behaviour (`age` still rejects `999`, `kind` still rejects `intern`, `email` still rejects `nope`).
- The ECHO `Ref` declaration survives the rewrite with its target DXN intact.

The remaining section is retained because the emitted _shape_ still has a within-version
consumer: `assistant-toolkit/src/skills/database/operations/schema-list.ts:33` returns
`toJsonSchema(schema)` to the LLM. That output shape is what a model sees when it inspects the
database, so changing it changes model behaviour — a same-version concern, not a cross-version one.

## Write path (v4 → the _v3_ stored format): not needed, but here is the gap

`SchemaRepresentation.toJsonSchemaDocument` is **not** a drop-in for `JSONSchema.fromAST`.
Emitting the ported `Person` schema and comparing to what v3 stored:

|                   | v3 stored                                                                                                        | v4 emitted                                                                              |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| envelope          | `{$schema, $id, entityKind, typename, version, type, properties, required, propertyOrder, additionalProperties}` | `{dialect, schema: {$ref}, definitions}`                                                |
| optional field    | bare type, absent from `required`                                                                                | `anyOf: [T, {type: "null"}]`                                                            |
| refinement        | inlined (`minimum`, `maximum`, `pattern`)                                                                        | nested under `allOf: [{…}]`                                                             |
| `Unknown` / `Any` | `{"$id": "/schemas/unknown", "title": "unknown"}`                                                                | `{"title": "unknown"}`                                                                  |
| ECHO `Ref`        | inline `{$id: "/schemas/echo/ref", reference: {schema, schemaVersion}}`                                          | `$ref: "#/definitions/Ref"` → `{"title": "Ref"}` — **the reference payload is dropped** |
| DXOS extensions   | `propertyOrder`, `typename`, `version`, `entityKind`, `echo`/`annotations`                                       | all absent; no injection hook                                                           |

ECHO would need its own emitter walking the v4 AST — roughly the same amount of code as the
current `withEchoRefinements` + `JSONSchema.fromAST` pair in `json-schema.ts`.

## The better option: store `SchemaRepresentation` instead

v4 ships a purpose-built, bidirectional, persistable schema encoding that v3 had no equivalent
of. `test/writeback.test.ts` round-trips the full `Person` schema through
`toRepresentation → toJson → fromJson → fromRepresentation` with all DXOS annotations intact
(`@dxos/echo/Type` comes back verbatim).

Two things had to be wired up, and both are the _sanctioned_ mechanism rather than a workaround:

1. **Declarations need a persistable identity.** Without a `representation: {id, payload}`
   annotation, serializing ECHO's `Ref` fails outright with
   `Missing key at ["references"]["Ref"]["representation"]`.
2. **Revivers are explicit — there is no global registry.** Anything a persisted schema can
   contain must be listed at revive time, _including built-in checks_: omitting them fails with
   `Missing reviver for effect/schema/isPattern`. `src/json-schema-compat.ts` exports
   `EchoRevivers` (7 built-ins + `RefReviver`) as the pattern.

This is strictly better than JSON-Schema-as-storage: it round-trips declarations and checks
losslessly, which the JSON Schema path provably does not.

## Recommended shape

1. Keep the legacy decoder (`src/json-schema-compat.ts`) permanently for existing spaces —
   it is ~280 LOC and already works.
2. Cut the write path over to `SchemaRepresentation`, versioned, with `EchoRevivers` covering
   ECHO's declarations and checks.
3. No stored-bytes migration is required either way, as long as the legacy decoder stays.
4. Consolidate the 80 files that import `effect/SchemaAST` directly down to `@dxos/effect`'s
   `ast.ts` **before** migrating — with `SchemaAST` effectively private in v4, that shrinks the
   unsupported-API surface from 80 files to one module.

## Caveats

- `4.0.0-beta.105`; the beta may still break these APIs.
- Six `as any` casts remain in `src/`, all at the dynamic-schema boundary (building a `Struct`
  from a runtime-computed field map). The v3 code has the same casts in the same places
  (`json-schema.ts` uses `(fields as any)[key] = …`). They would need the repo's no-cast
  treatment before this ships.
- `refToSchema` is a stand-in, not ECHO's real `Ref` declaration — it proves the reference
  payload survives, not that `Ref` resolution works.
- Validated against `corpus-v3.json` — all 18 ECHO types exported by `@dxos/types`, emitted by
  `toJsonSchema` on effect 3.21.4 (38 refs, 43 enums, 14 patterns, both `/schemas/*` sentinels).
  These are production type definitions, but still not schemas pulled from real user spaces;
  a user-authored type created through `schema-add` is the untested case.
