## Findings

- **F-1 — `app:QA-1.after.2`: `space.delete` times out and leaves the space half-deleted when EDGE signaling
  is unreachable.** Expected: the space leaves the space list. Observed: the invoke threw
  `Timeout [10,000ms]`; the space is listed as `SPACE_CLOSED` and a retry does nothing. Cause, from the
  stack (E-2) and `DataSpaceManager._tombstoneSpace`: `markSpaceDeleted` first appends the tombstone
  (`addDeletedSpace`), then `space.close()`, whose `SpaceProtocol.stop` → `leaveSwarm` →
  `EdgeSignalManager.leave` waits 10 s on an EDGE websocket that never connects here; the throw skips
  `space.delete()` and `this._spaces.delete(spaceKey)`, so the live list keeps a closed proxy, and the
  retry returns early from `isSpaceDeleted`. The trigger is environmental (below), but the ordering means
  any failed close strands the space until reload. Not fixed; reported.
- **F-2 — Environment: the headless helper launches Chromium without the sandbox proxy flags.**
  `testing/bin/qa-browser.mjs` passes only `--no-sandbox` under `PW_CHROMIUM_PATH`, so every HTTPS request
  from the page (EDGE HTTP and AI clients, signaling websocket) fails with `ERR_CONNECTION_RESET`, which is
  what produces E-1, E-3 and the timeout behind F-1. The `cloud-sandbox` skill documents the fix for exactly
  this case: `--proxy-server=$HTTPS_PROXY`, `--proxy-bypass-list=127.0.0.1;localhost`,
  `--ssl-version-max=tls1.2`, gated on `CLAUDE_CODE_REMOTE`. Not changed in this run (harness, not spec);
  until it is, every sandbox run will carry E-1 and fail `after` 2 the same way.
- **F-3 — Spec: `space.queryObjects` returns `{ results: [{ dxn, typename, label }] }`.** QA-1 steps 5 and
  8 read `rows.objects ?? rows` and would have thrown on `.map`; changed to `rows.results` (the label field is
  `label`, and each row also carries the `echo://` `dxn`). QA-2 (steps 1, 4, 7, 8) shares the old pattern and
  is not yet verified; left for its own run.
- **F-4 — Spec: `after` 2 had no assert and `after` 3 checked by name.** A non-ready space has no `name` in
  the snapshot, so `!spaces.some((s) => s.name?.startsWith('QA:'))` passed against a space that was still
  listed. Both now check by identity (`!$snapshot.spaces.some((s) => s.id === $space.id)`), which is the
  check that caught F-1.
- **F-5 — Spec: the `errors.length === 0` clauses (steps 3, 4, 7, `after` 3) are false in the sandbox
  for a background error logged during step 1** (E-1) that no step produced. The clauses were left as
  written; the report records the errors against the step where each first appeared (Execution Rule 11).
  The step-7 check that matters — no error logged by the deletion — holds: no new entry appeared.
- **Verified as written** (no change): `space.create` returns `{ id: <spaceId>, subject: [spaceId], space }`
  and does not switch the workspace; `markdown.create` returns `{ id: "echo://<spaceId>/<objectId>" }` and the
  document is placed in the space's root collection; `appToolkit.open` takes
  `root/<spaceId>/content/collections/<objectId>` and drives `layout.active` and `attention`;
  `space.removeObjects` returns `{ objects, parentCollection, indices, wasActive }` with `wasActive` holding
  the closed plank's path; the toast is `Document deleted` with `Close` and `Undo` (`Objects deleted` for two).
- **Spec, smaller edits:** `after` 1 gained an assert (`results.length === 0` plus the `Objects deleted` toast);
  step 7's note records the full `removeObjects` result shape; `given` gained "`dxos` is defined on the port",
  since the hook is mounted only at the end of `client.initialize()` and a probe before that sees `undefined`.
- `status:` set to `failing # 2026-09-09, smoke run`.
- Boot observation, before `$start`: on the cold dev server the shared-worker leader session timed out
  (`Worker connection timed out after 15000ms: opening worker leader session`), the app logged
  `client initialization failed` and `fatal dialog` at `20:46:19`, then the connection stole the stale leader
