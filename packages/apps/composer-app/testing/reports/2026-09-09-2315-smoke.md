## Findings

- **F-1 — `app:QA-1.after.2` still fails, with a different mechanism and a faster failure.** The
  proxy flags did not fix it, and comparing the two runs isolates why. In run 1 the page could not
  reach EDGE at all, so the delete blocked for the full `Timeout [10,000ms]` inside
  `EdgeSignalManager.leave`. In run 2 the websocket **does** connect and authenticate — the server
  log carries the client's own `identity`/`device` in each `server disconnected` payload — but EDGE
  drops it immediately and the client reconnects on a ~6 s loop (28 `edge connection socket error`
  and 28 `server disconnected` pairs during the run). `space.delete` fell into one of those drops
  and threw `Edge connection closed.` after 5601 ms. The end state is identical to run 1
  (`SPACE_CLOSED`, still listed, retry a no-op), which confirms the root cause named in run 1's F-1
  is in the app, not the environment: `DataSpaceManager._tombstoneSpace` appends the tombstone
  before `space.close()`, so **any** failure closing the space — a timeout or a dropped socket —
  skips `space.delete()` and `this._spaces.delete(spaceKey)` and strands a closed proxy in the live
  list, while `isSpaceDeleted` makes the retry a no-op. Two different transport failures producing
  the same stranded state is the argument that the ordering, not the transport, is the defect. Not
  fixed; reported.
- **F-2 from run 1 is resolved.** `ERR_CONNECTION_RESET` count went 55 → 0, and the
  `EdgeAiHttpClient Failed to fetch` error that polluted every snapshot in run 1 is gone: steps 1
  through 8 and `after` 1 all report `errors: []`. The `errors.length === 0` clauses in steps 3, 4
  and 7 — which run 1 recorded as false for a background error no step caused (run 1's F-5) — now
  hold as written. That closes run 1's F-5 as well.
- **F-3 — `after` 3 is now honestly red.** Run 1 recorded it as pass because the assert checked
  `name?.startsWith('QA:')` and the snapshot hides the name of a non-ready space; the tightened
  assert committed after run 1 (`s.id === $space.id`) catches the stranded space, which is what it
  was written for. Under today's spec run 1 would also have scored 9/11, so **the two runs are
  equal on the count and differ only in error noise and in how `after` 2 fails**.
- **F-4 — the environment now surfaces real HTTP statuses instead of resets.** With the proxy
  reachable, `org.dxos.operation.client.createAgent` fails with `HTTP code 500` (run 1: an RPC
  timeout), and the page logs one `401` and two `500` responses. These are EDGE rejecting an
  unauthenticated/unprovisioned agent, not a Composer defect, and none of them lands inside a
  `steps` window.
- **Verified again, unchanged from run 1** (same shapes on a different profile): `space.create` →
  `{ id, subject, space }` and no workspace switch; `markdown.create` → `{ id: "echo://…" }`;
  `queryObjects` → `{ results: [{ dxn, typename, label }] }`; `appToolkit.open` takes
  `root/<spaceId>/content/collections/<objectId>`; `removeObjects` →
  `{ objects, parentCollection, indices, wasActive }`; toasts `Document deleted` / `Objects deleted`
  with `Close` and `Undo`.
- **Spec:** no change was needed this run — every assert behaved as written, and `after` 2's note
  already describes the failure and caps the retry at one. Its wording attributes the timeout to
  "the cloud sandbox without proxy flags", which run 2 shows is too narrow: the step fails with the
  flags too. `status:` set to `failing # 2026-09-09, smoke run 2`, and the note now says a dropped
  connection strands the space the same way a timeout does.
- Boot observation: the shared-worker leader session timed out once again
  (`Worker connection timed out after 15000ms`), the app logged `client initialization failed` and
  two `fatal dialog` lines, then re-elected and initialized — same as run 1, and unrelated to the
  proxy flags.
