## From a question to a picture in one turn

Agents describe systems well and draw them badly. drawing splits the job: the agent says what connects to what, and
a layout engine decides where everything goes.

<CardGrid>
  <Card title="Install the skill" icon="download">
    One command teaches your agent the diagram language and gives it the `drawing` command.
  </Card>
  <Card title="Ask for a diagram" icon="comment">
    “Draw how a request moves through our services.” Your agent reads the code and writes .dx.
  </Card>
  <Card title="Get an SVG" icon="document">
    drawing lays it out in about a second, ready for a README, a pull request or a doc.
  </Card>
</CardGrid>

## Say what's related, not where it goes

Name the relationship and the right arrowhead follows. There are no coordinates to get wrong; add a placement hint
only when you want one.

## The SVG is the drawing

A .dx.svg is an ordinary image, and it also carries everything needed to edit it again. Nothing is locked in a
service you have to log in to.

<CardGrid>
  <Card title="Shows up anywhere" icon="seti:svg">
    GitHub, browsers and docs sites show it like any other SVG, with nothing to install.
  </Card>
  <Card title="Re-renders from text" icon="pencil">
    The .dx source rides inside the file, so the next change is a small diff, not a redraw.
  </Card>
  <Card title="Opens on a canvas" icon="puzzle">
    Import it into the drawing.sh app or a Composer space, and keep editing it with your team.
  </Card>
</CardGrid>

## Also in Composer

The same diagram editor is a plugin in Composer, DXOS's collaborative local-first workspace. There a diagram is one
more object in a space, next to documents, tasks and everything else your team keeps, and it works with Composer's
other plugins and agents. Composer is in early access; the drawing.sh app is the same canvas, open to everyone now.
