## Findings

Two full runs on 2026-10-21 (Claude Haiku 4.5 through the hosted EDGE AI proxy, limit 3). All three scenarios
passed both times; the transcripts above are from the second run.

1. **Fixed — a burst of queued prompts opened light threads blind.** In the first run all five serial prompts were
   queued at once. The scheduler started prompt 1 on main and opened light threads for prompts 2–4 before prompt 1's
   turn had written `turnBegin`, so their snapshot listed no siblings. Prompt 2 answered "I don't have a previous
   number" and prompt 3 replied to the separator instead of its request. `runLanes`
   (`thread-scheduler.ts`) now waits, before opening a light thread, until every running lane has consumed its
   prompt (`LaneRunner.started`). In the second run every thread saw its predecessors and waited for them.
2. **The model serializes dependent prompts on its own.** With siblings visible, each dependent prompt called
   `thread_wait` on the threads before it (sometimes on all of them, in parallel calls) and chained the answer
   correctly. The mix scenario's translation waited for the poem; the arithmetic answered at once.
3. **An unnecessary wait, once.** In the first run's parallel scenario, "What is 144 divided by 12?" waited 20 s for
   the unrelated slow lookup before answering. It did not recur in the second run. If it does, the separator could
   say more plainly that an independent request must not wait (`Transcript.snapshot`).
4. **No cross-thread confusion** once the snapshot is present: no thread answered another thread's request, and the
   merged main thread reads as a sequence of complete exchanges in merge order.
5. **Limit respected.** With four prompts behind a running turn and a limit of 3, the fourth light thread opened
   only after one of the first three ended.
