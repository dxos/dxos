# Tool-name audit

Every `Operation.make` definition in the repo with a `meta.key` (DXN), and the tool name the
model calls — derived in `Operation.toolName` ([Operation.ts](../../../compute/src/Operation.ts))
from the DXN key alone: strip the constant `org.dxos.function.` prefix, kebab-case each camelCase
segment, join with `-`. **`meta.name` is display copy and is never model-facing**, so rewording it
is free.

The same derivation backs `Skill.toolDefinitions`, so a skill's `tools` array and the runtime tool
names are one identifier space.

Generated by a source scan (regex over `Operation.make` meta blocks, resolving `makeKey` helpers
and `${CONST}` key templates); regenerate by re-running the scan after adding or renaming
operations. **Wired** marks operations referenced by a `Skill.toolDefinitions({ operations: [...] })`
— the model-facing set; unmarked rows are app/runtime operations that only become tools if a skill
binds them.

## Summary

- 374 named operations across 62 packages; 114 wired into skills; 5 operations have a key
  but no `meta.name` (display copy only — they still project as tools when a skill binds them).
- **No duplicate tool names among skill-wired operations.** Keys are registry-unique and the
  namespace segment prefixes the name, so cross-skill collisions are structurally impossible; a
  bind-time `invariant` in `createToolkit` fails loudly if one ever appears.
- 27 wired tools exceed 30 characters, all from keys shaped
  `org.dxos.plugin.<x>.operation.<verb>` (only `org.dxos.function.` is stripped).

## Analysis (implemented)

The display name doubling as the model's API identifier had four costs, all observed in this repo:

1. **Cosmetic edits were breaking changes.** Rewording `meta.name` renamed the tool the model calls
   and invalidated every memoized conversation fixture that recorded it.
2. **Collisions were live, not hypothetical.** `create` was claimed by plugin-markdown,
   plugin-script and plugin-sheet; `open` by plugin-markdown and plugin-transcription; `update` by
   plugin-markdown and plugin-script.
3. **Two identifier spaces.** `Skill.toolDefinitions` stored key-derived `ToolId`s while the runtime
   exposed name-derived strings, reconciled by a lookup that existed only to bridge the mismatch.
4. **Prompt drift was uncheckable.** Skill instruction texts named tools in free prose, and nothing
   tied the prose to the definition.

**Implemented: the tool name derives from the DXN key; never from display copy.**

- `Operation.toolName(op)` (and `Operation.toolNameFromKey` for a persisted record's key) is the
  single derivation, used by `makeToolName`'s replacement in the tool runtime and by
  `Skill.toolDefinitions`. The bridging lookup is gone: the resolver matches a registry record by
  re-deriving its name.
- `meta.name` is pure display copy — freely editable, never model-facing.
- Skill instruction texts interpolate `Operation.toolName(Op)` instead of hand-writing the name.
- `createToolkit` asserts tool-name uniqueness across the assembled session toolkit.

Trade-off accepted: keys are noun-first in places (`artifactAdd` → `project-artifact-add`, not
`add-project-artifact`), and `org.dxos.plugin.<x>.operation.<verb>` keys keep every segment. A key
rename remains available pre-launch where it grates.
