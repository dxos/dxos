# @dxos/agent-code-mode

## 0.12.0

### Minor Changes

- 2e4b170: New package `@dxos/agent-code-mode`: a `TurnProducer` that runs an agent's turns in "code mode". The model carries exactly one tool, `eval`, and reaches the workspace by writing code rather than by calling a tool per action. Operations bound by the conversation's skills are not projected as tools at all — each is a function the code calls — so a task spanning several of them costs one turn instead of one turn each. Only what the code prints goes back into the model's context — or, when a program prints nothing at all, the value it produced — and a failure is reported as output too, so the model can correct its own code rather than failing the turn.

  Two pieces are injected. `Sandbox` decides where the code runs: `Sandbox.inProcess` evaluates via `new AsyncFunction` here and now, which is NOT a security boundary — the code is compiled in the host realm and can reach host globals, and the timeout abandons a running evaluation rather than stopping it. `WorkerSandbox` runs the same code on a worker thread instead, which is what makes a timeout enforceable: the host TERMINATES the thread, so an evaluation that outran its budget stops — including a synchronous loop, which no in-process timeout can interrupt at all. The worker reaches the workspace over the boundary the client already speaks rather than a private protocol of its own: the host serves `ClientServices` on the worker's port, and the worker is an ordinary `EchoClient` connected to it, so the dialect's bindings are built THERE and the model's code sees live objects, real queries and the ordinary `Obj.update`. Added alongside those services, because that boundary has no service for them, are the turn's output, invoking a skill's operation (whose handler stays on the host with the conversation) and reporting the result. The one thing that cannot cross is the type registry — a registered type is a runtime class — so the worker rebuilds each one from its JSON schema, the way this codebase already ships schemas to a remote runtime. A worker bounds time and isolates crashes; it is still not a security boundary, since it shares the host's permissions. Install it with `WorkerSandbox.layer({ echo })` or `CodeModeOptions.sandbox`, passing the host services and the space to open, plus `spawn` for a runtime whose worker is not `node:worker_threads`. `Dialect` decides what the model writes: `PlainDialect` is a small async facade (`await query(...)`, `update(obj, mutator)`, `await ops['dxn:…'](input)`); `EffectDialect` is the repo's own ECHO API as an `Effect.gen` body (`yield* Database.query(Filter.type(types['...'])).run`), which reads like committed code but pins the sandbox to this process.

  Opt in with `makeCodeModeTurnProducer({ dialect })` as `AgentProcessOptions.makeTurnProducer` (or `AgentService.Options.makeTurnProducer`); `@dxos/agent-runtime` itself is unchanged — its queue, alarms, redelivery, delegation and hydration are untouched, and the default `AiSession` producer still applies when no producer is set.
