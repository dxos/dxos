## Before you start

The `Client` is the app's way into ECHO. It holds the databases of the spaces you belong to, on the device, and connects them to the network so peers can replicate them.

A client acts for an identity. The identity owns the spaces it creates, and other peers recognize it when it joins theirs. A space is a database that a set of identities replicate between them, and every object lives in exactly one space. The app keeps all its records in one space, called Contacts.

<Steps>

1. **Install the client.** `@dxos/client` holds the `Client`, and it brings `@dxos/echo` with it. The schemas these pages write also import `effect`.

   Until the next npm release, install the build of main these pages describe, from pkg.pr.new. The releases on npm are older and lack some of the APIs below.

   <Tabs>
     <TabItem label="pnpm">
       ```bash
       pnpm add https://pkg.pr.new/dxos/dxos/@dxos/client@20a14b9 effect@4.0.4
       ```
     </TabItem>
     <TabItem label="npm">
       ```bash
       npm install --save https://pkg.pr.new/dxos/dxos/@dxos/client@20a14b9 effect@4.0.4
       ```
     </TabItem>
     <TabItem label="yarn">
       ```bash
       yarn add https://pkg.pr.new/dxos/dxos/@dxos/client@20a14b9 effect@4.0.4
       ```
     </TabItem>
   </Tabs>

   Install any other `@dxos` package from the same build, with its name in place of `client`. The tutorial app's [package.json](/echo/project/package.json) lists every package it uses at that build.

   In a React app, install `@dxos/react-client` instead and follow the [React guide](/docs/echo/guides/react/).

2. **Configure the bundler.** In the browser, ECHO runs its database in a worker and loads WebAssembly in the page and in that worker. Vite needs four settings for it:

   - `vite-plugin-wasm` in `plugins` and in `worker.plugins`, so both can import WebAssembly.
   - `build.target: 'esnext'`, since the WebAssembly modules are loaded with top-level `await`.
   - `optimizeDeps.exclude` for `@dxos/wa-sqlite`, `@automerge/automerge` and `@automerge/automerge-subduction`. Vite's pre-bundling would move their WebAssembly files away from the code that loads them.
   - `optimizeDeps.include` for the CommonJS modules that only the database worker imports. Vite's dependency scan starts from the page, so it does not find them, and the worker cannot import a CommonJS module that Vite has not pre-bundled.

   `ConfigPlugin` loads the client's config from YAML files at the package root.

   <Snippet file="vite-config" title="vite.config.ts" />

   `@dxos/config/rollup-plugin` and `@dxos/config/esbuild-plugin` export the same `ConfigPlugin` for Rollup and esbuild. Node needs no bundler setup.

3. **Point the client at the network.** A client keeps its data on the device and reaches other devices through DXOS's EDGE network, which relays invitations and replicates spaces. The app's config, in `client.ts`, says where EDGE is and keeps the data across reloads. [Configure the client](#configure-the-client) covers loading config from files instead.

   <Snippet file="tutorial/client" region="config" />

4. **Open the app's space.** The app does this in one function, also in `client.ts`. `new Client` takes the app's types, which the next page declares, and the config. `createOpfsWorker` keeps the database in the browser's private file system. `initialize` opens local storage and connects to the network. The first time, the client needs an identity before it can create a space; [HALO](/docs/halo/overview/) covers identities and devices. After that, the app opens the space it made before.

   <Snippet file="tutorial/client" region="client" />

   `space.db` is the database the rest of the learning path reads and writes. `services` replaces the network: the embeds on these pages pass in-memory services, so each runs its devices in the page and keeps nothing.

</Steps>

## Configure the client

`new Client()` uses built-in defaults. Pass a `Config` to choose where settings come from. Each source is a function from `@dxos/config`, and earlier sources override later ones.

### Defaults from a file

`Defaults` returns the config in `dx.yml`. In Node it reads `config/default.yml` in your project instead.

<Snippet file="installation" region="defaults" />

### Local development

`Local` returns the config in `dx-local.yml`, so a development preset can sit beside the defaults. In Node, `Local` returns nothing.

<Snippet file="installation" region="local" />

### Environment variables

`Envs` maps environment variables to config paths, as listed in `dx-env.yml`.

<Snippet file="installation" region="envs" />

Each entry in `dx-env.yml` names a variable, the config path it sets, and its type:

```yml
LOG_FILTER:
  path: runtime.client.log.filter
  type: string

DX_PERSIST:
  path: runtime.client.storage.persistence
  type: boolean
```

<Aside type="tip">
  Vite exposes only variables prefixed with `VITE_`. To read any other variable at build time, list it in the
  `env` option of `ConfigPlugin`, as in step 2. Its value appears at the config path `runtime.app.env.MY_ENV_VAR`.
</Aside>

## What you can do now

You can install ECHO, configure a client for the browser or Node, and open the app's space with an identity.
