## Background

In a client-server app, you fetch a list from a server, and you fetch it again when you think it has changed. In
ECHO, we describe the records we want once, as a query, and the query can keep its results current.

A query has two parts:

- A **filter** says which objects match: by type, by field values, by text.
- A **query** wraps the filter and adds what to do with the matches: their order, a limit, or a step to the objects
  they reference or that reference them.

A query is a value, so building one runs nothing. `db.query(query)` runs it against the database on the device, which
means a query never waits on the network. You can then read the matches in two ways:

- `run` returns the matches once.
- `subscribe` returns them, then runs again whenever an object that could match changes, whichever peer changed it.

The client returns typed objects only for the types it knows. We pass the app's types to the client when the app
starts, in [Installation](/docs/echo/learn/installation/).

[The Filter guide](/docs/echo/api/filter/) lists every comparison and combinator.

We put each query in the component that runs it: the lists, search and count in `Contacts.tsx`, and an organization's
people in `RecordForm.tsx`.

## Steps

<Steps>

1. **List each type, sorted.** `Filter.type` selects the objects of a type, and `orderBy` sorts them by a field. The
   app's lists use these.

   <Snippet file="echo-tutorial/app/Contacts" region="by-type" lang="tsx" />

   Organizations and people sort by `name`, and events sort by `title`.

   `Filter.type` also matches field values. Pass them as a second argument, as in
   `Filter.type(Person, { name: 'Ada' })`, to select only the people named Ada.

2. **Search text.** `Filter.text` matches objects whose text contains the words, whatever their type. The space indexes
   text as objects are written. The search box uses this.

   <Snippet file="echo-tutorial/app/Contacts" region="search" lang="tsx" />

   Notice the `searching` check. The search runs only while the box has text, because an empty search has nothing to
   match.

   The search box runs its query with `useQuery`, a React hook from `@dxos/react-client/echo`. The hook calls
   `db.query` and subscribes to the result, as step 5 does by hand, and it re-renders the component when the results
   change. The [React guide](/docs/echo/guides/react/) covers the hook.

3. **Follow references backwards.** `referencedBy` steps from an organization to the people whose `employer` points at
   it.

   <Snippet file="echo-tutorial/app/RecordForm" region="employees" lang="tsx" />

   Here, `Filter.id` selects the one organization, and `referencedBy` follows `employer` backwards to its people.

4. **Run a query.** `db.query(query).run()` returns the matches once, typed, so each result is a `Person`. An
   organization's form lists its people with this.

   <Snippet file="echo-tutorial/app/RecordForm" region="run" lang="tsx" />

   `run` returns a promise, and `setStaff` stores the people when it resolves.

5. **Keep a query live.** `subscribe` calls back with the current results each time they change, and returns a function
   that stops it. `fire: true` calls back once at the start too. The toolbar's count of people uses this.

   <Snippet file="echo-tutorial/app/Contacts" region="live" lang="tsx" />

   The callback runs again whenever a person is added, changed or removed, on this peer or another.
   [Mutating objects](/docs/echo/learn/mutating-objects/) makes those changes.

</Steps>
