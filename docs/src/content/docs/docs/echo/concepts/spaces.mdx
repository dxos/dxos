A space is a database that a set of peers share and replicate, and it is the unit of sharing: a person shares a whole
space, not single objects.

## Model

Every object belongs to exactly one space, and `space.db` is the database that holds them. A device usually holds many
spaces at once, and each space has its own members.

<Snippet file="concept-spaces" region="database" />

### Storage

A device keeps each space in local storage: the browser's storage in a web app, files on disk in Node. In a browser the
client runs the database in a worker, apart from the page. It keeps an index of every space, and queries read from the
index as well as from the objects the page holds.

A write is finished, and visible to queries in the same tab, when the call returns. `db.flush` waits until pending
writes are on disk, and optionally until the index has them too.

### Replication

There is no server that owns a space. Each member holds a full copy of the space's data and exchanges changes with the
other members directly, over [WebRTC](https://en.wikipedia.org/wiki/WebRTC), or through [EDGE](/docs/edge/concepts/replication/), the DXOS sync
service. [MESH](/docs/mesh/concepts/transports/) carries both.
Reads and writes work offline, and the changes merge when the device reconnects, by the rules in
[Changes and branches](/docs/echo/concepts/changes/).

### The Hypergraph

The **Hypergraph** is every space this device holds, as one graph. `client.graph` queries across spaces and finds a
space's database by id. It also holds the **registry**: the types and objects registered in code, which a query without
`from` searches along with the database.

<Snippet file="concept-spaces" region="hypergraph" />

A reference can point into another space. It stores the qualified EID, `echo://<spaceId>/<objectId>`, and resolves if
this device holds or can reach that space.

<Snippet file="concept-spaces" region="cross-space" />

Use `space.db` for work inside one space, which is most work. Use the Hypergraph when the code cannot know the space
in advance, such as a search across everything a person has.

### Access

HALO decides who is a member of a space and what each member can do, with access control built on
[Keyhive](https://www.inkandswitch.com/keyhive/notebook/). [Spaces and membership](/docs/halo/concepts/spaces-membership/)
covers members and roles, and [Invitations](/docs/halo/concepts/invitations/) covers how a peer joins.

## Behavior

- Each member holds a full replica, so reads and writes work offline and merge when the peer reconnects.
- Several members can write to the same space at the same time. Their changes merge without a central authority.
- A reference into a space this device does not hold resolves to nothing: `tryLoad` returns `undefined`.

## Limits

- An object cannot move to another space. Copy it into the other space and remove the original.
- Sharing is per space. To share some objects and not others, put them in different spaces and link them with
  references.
