Two peers can change the same object at the same time, online or offline, and ECHO merges both changes without asking
either of them.

## Model

Each object lives in an [Automerge](https://automerge.org/) document, a CRDT. A peer writes to its own copy and the write
is finished when the call returns. <SpecCite item="org.dxos.echo.query#F-2.1" /> Peers then exchange changes, and every
peer that has seen the same changes ends up with the same state, whatever order the changes arrived in.

What "merged" means depends on the kind of value:

| Concurrent change                                | Result                                                       |
| ------------------------------------------------ | ------------------------------------------------------------ |
| Different fields of one object                   | Both writes kept                                             |
| The same scalar field, such as a status          | One value wins, the same on every peer                       |
| A whole string assigned twice                    | One string wins, as with any scalar                          |
| Characters inserted or deleted with `Text`       | Both edits kept, interleaved                                 |
| Items inserted into one array                    | Both kept; the order of the two new items is decided by ECHO |
| One peer edits an object another removes         | The removal stands                                           |

The table explains the choice between assigning a string and editing it with `Text`. Assignment replaces the value;
`Text.splice` and `Text.update` change characters, so two people typing in the same field both keep their work.

## Behavior

- A local write shows in query results and reaches subscribers before the writing call returns.
  <SpecCite item="org.dxos.echo.query#F-2.1" />
- A subscriber that writes from inside a notification makes a separate commit, with its own notification after the
  first. <SpecCite item="org.dxos.echo.query#F-2.2" />
- A peer that was offline keeps writing to its copy. When it reconnects, peers exchange the changes each is missing and
  merge them by the rules above. Nothing is rejected for being late.
- Each change records the device that made it. `Obj.getChanges` lists an object's history, so an app can see that two
  devices wrote the same field and ask a person to confirm the result.

## Limits

- ECHO does not know what your fields mean. When one peer sets `status: 'done'` and another sets `status: 'doing'`, one
  value wins and the other is not flagged. If the loser matters, model the intent instead: record each person's choice in a
  field of its own, or append events to a [feed](/docs/echo/guides/feed/) and derive the state from them.
- Invariants across fields or objects are not kept. Two peers can each make a valid change whose merge breaks a rule such as
  "at most one task is in progress". Check such rules when you read, not only when you write.
- A schema change is not merged with data written under the old version. Use a new version and a migration.
