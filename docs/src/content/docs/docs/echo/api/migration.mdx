A migration moves objects from one version of a type to another, or renames a type. Migrations run in each space, and
must give the same result on every peer, so that peers that migrate the same object at the same time write the same
values. [Types and schema](/docs/echo/concepts/types/#versions-and-migrations) explains when a change needs one.

## Migrate to a new version

`Migration.define` takes the old type, the new type and a `transform` that returns the new fields from the old object.
The object keeps its id. `onMigration` runs after, for changes to other objects, such as making a child object from a
field the new version drops.

<Snippet file="guide-migration" region="define" />

## Rename a type

`Migration.defineRename` points every reference to the old typename at the new one, and keeps each reference's version.
A reference that already names the new typename is left alone.

<Snippet file="guide-migration" region="rename" />

## Upgrade a content format

Some types store data that ECHO does not parse, such as the shapes of a drawing, with a field that names its format. Mark
that field with `ContentVersionAnnotation`. `Migration.defineContent` upgrades the content from one format to the next,
and steps chain: content at format 1 goes through every step to the newest. `since` records the release that first ships
the step, which says when it can be deleted.

<Snippet file="guide-migration" region="content" />

`Migration.upgradeContent` runs the same chain in memory, for content that arrived before the migration ran.

## Run migrations

A Composer plugin contributes its migrations, and Composer runs them on every space once the plugin is active. The docs
do not yet cover running migrations outside a plugin.

## Members at a glance

| Member | Summary |
| --- | --- |
| `define` | Migrate objects from one version of a type to another |
| `defineRename` | Rename a type and repoint references to it |
| `defineContent` | Upgrade a content format inside a type |
| `upgradeContent` | Upgrade content in memory |

The full list is in the [API reference](/docs/additional-resources/api-reference/).
