An operation is the unit of compute in DXOS. It is a typed action that you define once. Whoever needs it runs it: a
person through the UI, an agent as a tool, or a trigger. A trigger is an object that starts an operation on a schedule
or an event.

## Model

An HTTP endpoint has a path, a request body and a response body. An operation has the same three parts: a key, an input
schema and an output schema.

### Definition

A **definition** is the value that `Operation.make` builds from metadata and two schemas:

- The metadata, `meta`, holds the key, a name, a description and an icon. The **key** is a DXN, such as
  `com.example.operation.stashedLink.markRead`, and it names the operation everywhere it runs. The description is
  what an agent reads when it decides whether to call the operation.
- The input and output schemas are Effect schemas. Their field descriptions tell people and agents what to pass.
- A definition can also list the ECHO types it uses, so the types are known where it runs remotely, and the
  `services` its handler needs.

### Handler

A **handler** takes the input and returns an Effect that produces the output. `Operation.withHandler` attaches one to a
definition.

<Snippet file="plex-tutorial/src/operations/mark-read" region="handler" />

`handler` is the `MarkRead` definition with its handler attached. The handler can call `Database.resolve` because the
definition lists `Database.Service`. It then sets `read` to `true` inside `Obj.update`.

The definition and the handler are separate values, so a package can publish the definition for others to call
without shipping how it runs.

`Operation.lazyHandler` names the module that holds the handler. Use it when the code should load only on the first
call.

A **handler set** is a group of handlers that a runtime loads together. A PLEX plugin contributes one through a
capability. See PLEX's [Operations](/docs/plex/concepts/operations/).

### Invoker

The **invoker** runs an operation for a caller. It does four things in order:

1. It finds the handler by the definition's key.
2. It checks the input against the input schema.
3. It runs the handler with the services it declared.
4. It checks the output.

### Registry

The **operation registry** holds each definition as an ECHO object, so agents and the MCP server can search the
operations a space offers. A definition whose metadata sets `skipRegistry` is left out of it.

### Annotations

A definition carries hints for its callers:

| Annotation | Says |
| ---------- | ---- |
| Mutation   | Whether the operation changes nothing, writes, or destroys data         |
| Idempotent | Whether running it twice with the same input has the same effect as once |
| Visible    | Whether people can pick it, as in a trigger's operation picker. Unmarked operations are hidden |

## Behavior

- One definition serves every caller. A button, the command palette, an agent and a trigger invoke the same key with
  the same input.
- Errors are typed. A handler fails with tagged errors that the caller catches by tag. If you invoke a key that no
  handler set serves, the call fails with `NoHandlerError`.
- A handler can stop early when its run is cancelled. It reads the run's `AbortSignal` from `Cancellation.signal` in
  `@dxos/compute`, and hands the signal to work that can stop, such as a `fetch`.
- The runtime that runs the operation fires the signal. In the app, it fires when the
  [process](/docs/edge/concepts/processes/) is terminated, and the runtime then interrupts the handler. On EDGE, it
  fires when the client asks to cancel the run, and the handler is not interrupted.
- If the runtime provides no cancellation, the signal never fires.
- An operation can invoke other operations. The call is linked to the caller's [process](/docs/edge/concepts/processes/),
  so the trace shows which call started it.
- When you deploy an operation to EDGE, EDGE assigns it a deployment id. A client can invoke it there by that id or by
  its key.
- Every call writes its start and end to the [trace](/docs/edge/concepts/traces/).

## Limits

- Input and output must be serializable, because a call may cross to a browser worker or to EDGE. Pass ECHO objects
  by reference.
- A handler gets only the services its definition declares and the ones every process has. It does not get the UI.
- An operation that sets `skipRegistry` is not in the operation registry, so agents and the MCP server cannot find it.
  Use it for an operation that only makes sense in the UI.
