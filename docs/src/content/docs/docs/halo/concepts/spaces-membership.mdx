A space's membership is a Keyhive group. It holds the identities that may replicate the space, each with an access
level.

[Spaces and databases](/docs/echo/concepts/spaces/) covers the data in a space and how it replicates. This page covers
who gets it.

## Model

Two peers sync a space with no server between them. Who says the other peer may have the data? Each peer does. It
keeps the space's membership and checks against it.

A **member** is an identity that the space has admitted, named by its DID. Each member has one **access level**. The
levels are ordered, and each includes the one before:

| Access  | The member can                                             |
| ------- | ---------------------------------------------------------- |
| `pull`  | Receive the space's data in encrypted form. A sync service is such a member |
| `read`  | Read the space                                             |
| `edit`  | Read and change the space                                  |
| `admin` | Change membership. It can invite, change access levels and remove members |

The identity that creates a space is its first admin. The levels come from
[Keyhive](https://www.inkandswitch.com/keyhive/notebook/), and the API calls a member's level its `role`.

A **membership policy** says whether the space takes new members. A space has one of two policies:

- `invite` admits new members through [invitations](/docs/halo/concepts/invitations/).
- `locked` admits no one new. Use it for a space that should stay private to one person or a fixed group.

**How access is checked.** Membership is a graph of signed delegations and revocations. A **delegation** admits a
member with an access level, such as "admit this identity with `edit`", and a **revocation** removes one. Each is
signed by a member allowed to make it, and no member can delegate more access than it holds.

Every peer keeps the graph and checks each operation against the members it already trusts. A peer needs no server
to decide whether to accept another peer's changes.

Delegations and revocations converge. Peers that have seen the same ones agree on the membership, whatever order they
arrived in.

**Who can revoke whom.** An admin can revoke any member. Any other member can revoke only the members it has **causal
seniority** over.

A member has causal seniority over the members whose delegation depends on its own, because it admitted them or
admitted whoever did. A revocation that breaks this rule is refused.

**Encryption.** The **group key** encrypts a space's changes. Keyhive keeps it for the members with `read` or more,
so a member with `pull` stores and relays the changes without reading them. When membership changes, the key changes
too.

**EDGE.** EDGE, DXOS's always-online peer, joins a space as a `pull` member. It holds and relays the encrypted
changes, so devices that are never online together still sync, and it cannot read them.

An admin who gives EDGE more than `pull` makes the space readable on EDGE, so EDGE can index it, run operations and
agents on it, and send it to AI. EDGE still stores the data encrypted and keeps the keys apart from it, and reading
the data needs both. EDGE brings the two together while an operation works on the data. That is the trade-off for
using EDGE's indexing, compute and other services.

An [agent device](/docs/halo/concepts/identities-devices/) is a separate grant, made by one identity. The agent
device is one of that identity's devices, and EDGE holds its key. Its feed is admitted to the identity's spaces, and
EDGE uses it to write credentials there when no member's device is online, such as the one that admits a new device's
feed. It signs credentials and does not read the space's data.

<Aside type="caution" title="What runs today">
HALO's API describes Keyhive, and the implementation under it has not moved to Keyhive yet. Until it does, spaces
replicate through EDGE without end-to-end encryption, so EDGE can read every space it replicates. `pull` cannot be
granted yet, and only an admin can change a space's membership.
</Aside>

## Behavior

- An admin can invite members, change a member's access level with `Space.updateMemberRole` and remove a member with
  `Space.removeMember`.
- A guest who joins through an invitation started with `Space.share` is an `admin`.
- Peers reject changes from an identity whose access level does not allow them.
- Removing a member is a revocation, and it rotates the space's key. The removed member stops receiving new changes,
  and could not decrypt them if they did.

## Limits

- Removal does not reach data the member already has. A removed member keeps their copy of everything they could read
  before.
- Access applies to the whole space. To share part of the data with fewer people, put it in a separate space.
