---
title: Invitations
description: How a device or a person is let into an identity or a space.
---

An invitation is a short-lived offer from a host to let one guest in: a new device into an identity, or a new member into
a space. It ends in a delegation, the same signed statement that every other change to membership is.

## Model

In a web app, you invite someone by sending a link, and a server adds them to the team when they open it. In HALO,
the host admits the guest, and the record of it is a signed delegation.

**Kinds.** An invitation is one of two kinds:

- A `device` invitation admits a device to the host's identity. `Identity.share` makes one.
- A `space` invitation admits another identity to a space. `Space.share` makes one.

**Types.** The type says whether the host has to be online:

| Type          | Behavior                                                       |
| ------------- | -------------------------------------------------------------- |
| `interactive` | Host and guest are online at the same time and talk directly   |
| `delegated`   | The guest can redeem it while the host is offline              |

An invitation ends when the host admits its first guest. The `multiUse` option keeps it open, so more than one guest
can redeem the same code.

**Auth methods.** The auth method is how the guest proves it is the intended guest:

| Auth method        | Proof                                                            |
| ------------------ | ---------------------------------------------------------------- |
| `none`             | None. Anyone with the invitation code is admitted                |
| `shared-secret`    | A short authorization code the host shows, typed in by the guest |
| `known-public-key` | A signature from a key the host named in advance                 |

The invitation code and the authorization code travel by different routes, for example a link in a chat and a code read
aloud. This means someone who intercepts only the link cannot get in.

**Admission.** Two things happen when a guest is let in:

1. The two sides exchange **contact cards**. Each card names an identity or device, and carries the keys others need
   to encrypt to it and check its signatures.
2. The host writes a [delegation](/docs/halo/concepts/spaces-membership/) that admits the guest, signed by a member
   allowed to make it.

Peers check that delegation like any other. This means nothing about the invitation itself has to be trusted after it
ends.

## The flow

`Invitation.events` follows a flow from either side. An interactive invitation with `shared-secret` runs like this:

1. The host calls `share`. The flow emits `connecting` and waits for a guest.
2. The host sends the invitation code to the guest.
3. The guest calls `join` with the code. The two find each other through the signaling service and open an encrypted
   connection. Both flows emit `connected`.
4. Both flows emit `readyForAuthentication`. The host's event carries the authorization code, which the host passes to
   the guest by another route.
5. The guest calls `Invitation.authenticate` with the code. Both flows emit `authenticating`.
6. The host checks the code. The two sides exchange contact cards, and the host writes the delegation that admits the
   guest. Both flows emit `success`, and the guest's event names the space or the identity it joined. The guest
   then finds the space in `Space.spaces`, or the identity in `Identity.identity`.

Any step can end in `cancelled`, if either side calls `Invitation.cancel`, or in `error`.

## Delegated invitations

A delegated invitation works while the host is offline. Use it when host and guest may not be online at the same
time.

The host publishes **prekeys** in advance. A prekey is a one-time key the guest can encrypt to without the host there.
The host also signs the operations that admit whoever redeems the invitation, and EDGE holds them until the guest
connects.

The guest then reads the operations, checks the signatures, and joins with the access the host chose.

## Limits

- If an invitation is never redeemed, it expires. Start a new one.
- If the guest sends a wrong authorization code, the flow goes back to `readyForAuthentication`, and the guest can
  send another. After three wrong codes the flow ends with an `error` event, and the guest must join again.
- `none` admits anyone who sees the code. Use it for demos and for codes you show only on a screen you control.
