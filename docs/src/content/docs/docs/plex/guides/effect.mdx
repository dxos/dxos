By the end of this guide, your module reads the capability manager as a service, your plugin contributes a layer, and
your operation names the services it needs. All three work because a module's body and an operation's handler are
[Effects](https://effect.website/).

In Effect, a service is a value that code asks for by a tag, and a layer is the recipe that builds one.
[Managing Services](https://effect.website/docs/requirements-management/services/) covers both.

## Read capabilities as a service

Inside a module, the capability manager is `Capability.Service`. `Capability.get`, `Capability.getAll` and
`Capability.waitFor` read it for you. Yield the service itself when you need the manager, for example to read a
capability from a callback, where you cannot `yield*`.

## Contribute a layer

A service that an operation uses comes from a layer. To supply one, contribute a `LayerSpec` to
`Capabilities.LayerSpec`. The spec says what the layer provides, what it requires and how widely one instance is
shared. The `affinity` field sets that width:

- `'application'` builds the layer once, and every operation shares it.
- `'space'` builds one for each space.
- `'process'` builds one for each process, and removes it when the process ends.

## Declare an operation's services

An operation lists the services it needs in `services`. When you invoke it, the runtime builds them from the layer
specs that plugins contributed. The handler yields them like any Effect service.

If an operation's services have no layer, the operation fails when it is invoked, not when the plugin loads. A test
from [Testing](/docs/plex/guides/testing/) catches it.

## Limits

- Never run an Effect with `Effect.runPromise` inside a module. Return it, so the plugin manager can interrupt it
  when the module deactivates.
- A layer spec's service is in-process. A service that must run on [EDGE](/docs/edge/overview/), the always-online
  peer that DXOS runs, needs a layer there too.
