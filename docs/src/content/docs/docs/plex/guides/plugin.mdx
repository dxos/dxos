`Plugin` defines a plugin from its metadata and its modules. A plugin does nothing by itself. Its modules contribute
everything it adds to the app.

## Define a plugin with its metadata

A plugin's metadata names it. The key is an NSID, a reverse-domain name whose last segment is camelCase, such as
`com.example.plugin.hello`.

`DXN.make` wraps the key because `Plugin.makeMeta` takes a DXN, the DXOS name for a resource, and not a string. A key
with a hyphen in its last segment fails here, when the file is imported.

If your package has a `dx.config.ts`, describe the same metadata there, and `Plugin.config` derives the `meta`.
[Create a plugin](/docs/plex/learn/create-plugin/) shows that form.

## Add modules and choose their activation events

A module declares the capabilities it `provides` and `requires`, and optionally the event it `activatesOn`. The plugin
manager activates a module when its event fires and every singleton capability it requires has been contributed.

**Example** (Declaring a module that activates at startup)

<Snippet file="app-framework-guide-plugin" region="module" />

`activatesOn: ActivationEvents.Startup` makes `GreetingModule` part of the app's boot. Leave the field out and the
module waits for `Idle`, which the app fires when it is idle after startup.

A module's body can sit in the same file or load later:

- `Capability.inlineModule` keeps the body in the same file.
- `Capability.lazyModule` loads the body from another chunk when the module activates. Use it when a plugin has
  many modules, so the plugin costs little at startup.

`import` of the body's file, which is what moves the body into a chunk of its own.

## Contribute capabilities from a module

A module body returns the contributions it declared in `provides`. The compiler checks the match. A missing or
undeclared contribution is a type error at `Plugin.addModule`.

`GreetingModule` above returns one contribution, made with `Capability.contribute`. See
[Capability](/docs/plex/guides/capability/) for how to declare and request capabilities.

## Describe the plugin in `dx.config.ts`

A plugin that is published describes itself in `dx.config.ts`. `Plugin.config` takes these parts:

- The metadata.
- The registry's fields, such as tags.
- The modules. You make each one with a module maker from `AppCapability`, a function that makes a module for one
  capability and names the file to load.

`Plugin.config` returns `meta` and `make`, so the registry reads the plugin without importing its modules.

`config` is the file's default export, which the plugin's dev server and build read. `meta` and `make` are named
exports for code that creates the plugin itself, such as a test.

[Testing](/docs/plex/guides/testing/) starts a plugin made this way in a headless app.

## Members at a glance

| Member | Summary |
| --- | --- |
| `makeMeta` | Make a plugin's metadata from its key, name and description |
| `namespace` | Hold a plugin's key and make capability tags under it |
| `define` `addModule` `make` | Build a plugin from its metadata and modules |
| `config` | Define a plugin and its modules in `dx.config.ts` |
| `getMetaFromConfig` | Derive the metadata from a `dx.config.ts` config |
| `activate` | Fire an activation event from a module |
| `Service` | The plugin manager, as an Effect service in a module's body |
| `Capability.inlineModule` `lazyModule` | Declare a module with its body inline or behind a loader |

The full list is in the [API reference](/docs/plex/resources/api-reference/).
