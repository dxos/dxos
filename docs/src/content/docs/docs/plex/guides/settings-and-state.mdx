By the end of this guide, your plugin has settings that sync and state that stays on one device, and a component that
reads and writes both.

A plugin keeps these two kinds of value outside ECHO:

- Settings are choices the person makes, such as a default view. They follow the person to every device.
- State belongs to one device, such as the last item opened or a panel's width. It does not sync.

Keep them apart. If you store a device-only value as a setting, it moves to the person's other devices, where it is
wrong.

## Settings

Describe the settings with a schema, and contribute it with `AppCapabilities.Settings`. The app renders a form for
it on the settings page, using each field's `title`, and syncs the values.

`KvsStore.make` gives an [atom](/docs/plex/resources/glossary/#atom) that holds the values, with defaults for a first
run. An atom is a reactive value that code subscribes to.

## State

Device state is an atom that the plugin keeps to itself. Declare a singleton capability for it on the plugin's
namespace, and leave it out of `AppCapabilities.Settings`, because the app syncs only what a plugin contributes
there. Store it under a key of its own, `${key}.state`, so it does not share the settings' storage.

## Read and write them

Both are atoms that the plugin contributes as its own capabilities. In a component, you read and write them with two
hooks from `@dxos/app-framework/Hooks`:

- `useAtomCapability` returns the atom's value and re-renders the component when it changes.
- `useAtomCapabilityState` returns the value and a function that updates it, like `useState`. Use it when the
  component changes the value.

Each hook calls `useCapability` for the atom and then reads it, so you do not call the atom hooks `useAtomValue` and
`useAtomSet` yourself.

## Limits

- Settings are not ECHO objects, so they do not appear in a space or in search.
- Change a settings schema only by adding optional fields, so values stored by an earlier version still decode.
