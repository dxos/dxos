By the end of this page, the inspector below loads your plugin, named Stash, from your machine. The plugin has one
module so far, for its strings. The next four pages give it a type, an operation, a place in the navigation tree and
a view.

## Background

A plugin is a set of modules. Each module activates on an event and contributes to capabilities, the typed slots that
other parts of the app read. [The PLEX plugin](/docs/plex/learn/the-plex-plugin/) explains how they fit.

We define the whole plugin in one file, `dx.config.ts`, in step 3. Each module's code lives in its own file, which
loads only when the module activates.

A **manifest** is a `manifest.json` file that holds the plugin's metadata and says where its code is. The plugin's
dev server makes it from `dx.config.ts`, and the inspector loads the plugin from it in step 5.

## Steps

1. **Create the package.** Make a directory for the plugin with a `package.json` and a `vite.config.ts`.

   <PluginPackage />

   Then install the dependencies in that directory:

   ```bash
   npm install
   ```

   The `@dxos/*` packages are pinned to the build these docs run, so the inspector on each page can load your plugin.
   [Publishing a plugin](/docs/plex/publishing-plugins/) says what to pin them to before you publish.

   `composerPlugin` serves the plugin from Vite's dev server on port 3967. It also serves the manifest, at
   `http://localhost:3967/manifest.json`.

2. **Name the plugin.** The plugin's key is an NSID, a reverse-domain name that no other plugin uses. Its last segment
   must be camelCase. Put the key in a file of its own, so `dx.config.ts` and the plugin's modules can both import it.

   <Snippet file="plex-tutorial/src/namespace" region="namespace" />

   `StashNamespace.key` is `com.example.plugin.stash`, and every other file reads the key from here.

3. **Describe the plugin.** `Plugin.config` takes the plugin's metadata and its modules. It returns the plugin's
   `meta` and a `make` function that the app's plugin manager calls to create the plugin.

   <Snippet file="plex-tutorial/dx.config" region="config" omit="translations, schema, operation, app-graph, surface, skill" />

   The dev server reads the file's default export. `modules` starts empty, and the next step adds the first module.

   The `tags` field starts with a quality tier. A new plugin is `labs`.

4. **Add the first module.** Translations give the plugin's strings their text. The module's file lists the
   translation resources by language and namespace. For now it has one namespace, for the plugin's own strings.

   <Snippet file="plex-tutorial/src/translations" region="translations" omit="type" />

   Add the module to `modules` in `dx.config.ts`. A **module maker** is a function that makes a module for one
   capability, and `AppCapability.translations` is the maker for translations. It fixes the capability the module
   contributes to, so `dx.config.ts` names only the file to load.

   <Snippet file="plex-tutorial/dx.config" region="translations" />

   This maker names no activation event, so the module activates once the app is idle after startup.

5. **Load it in the inspector.** Start the dev server in the plugin's directory with the package's `dev` script:

   ```bash
   npm run dev
   ```

   Then click **Load dev plugin** below. The browser asks to reach devices on your local network. Allow it, because
   your plugin's code comes from your machine.

   The inspector lists your plugin's modules on the left, with Translations active, and shows its strings by
   namespace. **This page adds** turns to a check once the module loads.

   <InspectorEmbed adds={['translations']} />

   Leave the dev server running for the rest of the path. After an edit, click **Reload** in the inspector.

## What you can do now

You can name a plugin with a namespace, describe it in `dx.config.ts`, add a module with a module maker, and see what
the plugin contributes in the inspector.
