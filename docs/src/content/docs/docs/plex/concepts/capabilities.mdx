A capability is a typed slot that modules contribute values to and other modules read. This means plugins extend
each other without importing each other.

## Model

In most apps, one feature uses another by importing it. A menu that lists every export format has to import each
exporter, and you edit the menu each time you add one. With capabilities, the menu reads a slot, and each exporter
contributes to it.

A capability is a **tag**, which is an NSID plus the TypeScript type of its values. You declare one in two ways:

- `Capability.make` declares a multi capability, which any number of modules contribute to.
- `Capability.makeSingleton` declares one with exactly one provider.

A module **contributes** by returning `Capability.contribute(tag, value)` from its body. It lists the tag in
`provides`.

A module **requests** with `yield*` on the tag, or with `Capability.getAll` for every contribution to a multi
capability. It lists what it cannot run without in `requires`.

The capability manager holds every contribution. It is the `Capability.Service` in a module's Effect context, and the
plugin manager owns it.

## Behavior

- The compiler checks a module's body against its `provides`. If the body returns a contribution the module does not
  list, it does not compile.
- The plugin manager activates a module only after every singleton capability in its `requires` has a contributor.
  This means a module can read them without waiting. A multi capability never holds a module back. The module reads
  whatever has been contributed so far.
- You can read a capability in four ways, and each suits a different need:

| Call | Returns | When |
| --- | --- | --- |
| `Capability.get` | The first contribution, or fails with `CapabilityNotFoundError` | The capability must be there. |
| `Capability.getAll` | Every contribution, possibly none | A multi capability. |
| `Capability.waitFor` | The first contribution, once one arrives | It is contributed later than this module runs. |
| `Capability.atom` | An atom of every contribution | Reactive code that should update as plugins come and go. |

- One plugin extends another by contributing to a capability the other reads. Stash adds itself to the Space

- Contributions change after startup, when a module activates late or a person turns a plugin on or off.
  `Capability.contributions` and `Capability.atom` stay current. A value read once with `getAll` does not.
- When a module deactivates, its contributions are removed and its finalizers run.

## Limits

- A singleton capability with two providers is an error. Use a multi capability for anything more than one plugin
  might contribute.
- The capability manager does not check a value against anything but its TypeScript type. This means two plugins
  that build against different versions of a capability's type are not caught at runtime.
- Capabilities are in-process. They do not cross from the app to a worker or another device.
